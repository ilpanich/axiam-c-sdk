1/*
2 * AXIAM C SDK — WebAuthn / passkeys (CONTRACT.md §24).
3 *
4 * WHAT IS HERE, AND WHAT DELIBERATELY IS NOT.
5 *
6 * The six relying-party wire operations, plus §24.6a's JSON bridge. What is not
7 * here is §24.6b's linked-API ceremony helper: a C program has no authenticator
8 * — there is no platform API to link on the targets this SDK serves — and
9 * §24.6b rule 2 forbids emulating one in software, because a "credential" held
10 * in process memory is not a second factor.
11 *
12 * That is a statement about convenience, not about capability. §24.6a is the
13 * seam that makes it so: axiam_webauthn_request_json() hands out the challenge
14 * in the exact JSON form every platform authenticator API takes, and every
15 * *_finish takes the platform's response JSON back as a string, byte for byte.
16 * An embedded gateway that fronts a browser, a mobile app talking to a C
17 * service, or a test harness driving a virtual authenticator all use the same
18 * two seams.
19 *
20 * THE SERVER OWNS THE OPTIONS (§24.0). Nothing in this file defaults a field,
21 * validates one, or re-encodes a buffer. The challenge arrives as JSON text and
22 * leaves as JSON text; the authenticator's response is spliced into the request
23 * body without being parsed into a model and printed back out. A signed buffer
24 * that makes a round trip through a JSON model is a signed buffer that can come
25 * out different.
26 *
27 * OWNERSHIP. Every out-parameter carrying heap memory has a matching _dispose,
28 * and every one is safe on NULL and on a zeroed struct, so a caller can dispose
29 * unconditionally on the error path.
30 */
